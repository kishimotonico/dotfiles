# omp Implementation (herdr常駐セッション)

herdrペイン上の常駐 omp (oh-my-pi) に作業を委譲し、`herdr-msg` でやり取りする。`HERDR_ENV` が `1` でなければherdr管理下にないので、その旨を伝えて codex-impl 等の非対話委譲を提案する。

役割分担が codex-impl / cursor-impl と違う。統括的な作業(細かい仕様や設計の調整、実装の管理、バッチ分割やブランチ運用の計画)も実質的な作業(実装・検証・コミット・マージ)もすべてompに任せる。Claude側(Fable/Opus)はアドバイザー・監督に徹する:

- 依頼の整理(達成したいこと・制約・規約の所在をompに渡す)
- ompからの相談・質問への助言。ユーザー判断が要る論点は自分で決めずユーザーへ
- 成果のレビューと裏取り、マージ承認のゲート
- ユーザーへの報告

計画を自分で細かく立てたり、ompの作業に割り込んで自分で実装したりしない。

メッセージのやり取りは pane-consult スキルの作法に従う。

## セットアップ

既存のompペインがあればそれを使う。`herdr-msg list omp` で確認し、以降の宛先にはそのterminal_idを控える。ユーザーが常駐させているペインを流用した場合、後始末で閉じない。

なければ作る:

```bash
pane=$(herdr pane split "${HERDR_PANE_ID:?}" --direction down --no-focus | jq -r '.result.pane.pane_id')
herdr agent start omp --kind omp --pane "$pane" --timeout 60000 -- --approval-mode yolo
term=$(herdr agent get "$pane" | jq -r '.result.agent.terminal_id')
```

- `--approval-mode yolo` は必須。委譲先の承認プロンプトに応答できる人がいないうえ、コミット・マージまで任せるので書き込み承認も自動化する。信頼できるリポジトリでのみ使う(omp v18時点のフラグ。`--auto-approve` でも同じ)
- 以降の宛先は `$pane` でなく `$term` を使う。pane IDはペインの開閉で振り直されるが、terminal_idは同じターミナルを指し続ける。複数バッチの長時間運用ではこの差が効く
- ompのモデルとコンテキスト長は `~/.omp/agent/config.yml` の `modelRoles.default` で分かる。読めない・判断できないときだけユーザーに確認する

## 依頼書ファイル方式

herdr-msgのメッセージは1行に限られるので、依頼は自己完結の依頼書ファイルに書き、メッセージには概要とパスだけを入れる。

依頼書に含める項目:

- 背景と達成したいこと(ompはこの会話の文脈を知らない前提で書く)
- プロジェクト規約の参照先(AGENTS.md等のパス)
- タスク一覧または要求仕様。タスク一覧はユーザーから渡された粒度のまま転記し、無ければ要求仕様だけを書いてタスク分解はompに任せる
- 進め方の約束(後述の運用ルール)と裁量の範囲
- 完了報告の形式(後述)と「返信先はconsultメッセージ末尾のreplyヒントの値を使う。依頼書からの推測は禁止」の一文

```bash
details=$(mktemp /tmp/omp-impl.XXXXXX.md)
# Writeツールで依頼書を $details に書く
herdr-msg consult "$term" "<概要1行>。詳細は $details を読んで。完了報告・質問はreplyで"
```

送信後はポーリングせずターンを終える。質問と完了報告は `[reply from=…]` として届く。

## 進め方の約束(依頼書に書く運用ルール)

計画の中身はompに任せるが、次の枠組みだけ約束として渡すと安定する(監査タスク15件を5バッチで完走した実績パターン):

- 作業量が多い場合、ompがバッチに分割し、まず全体計画(バッチ一覧)を立ててから進める。1バッチの粒度はコンテキスト長に余裕を持たせる(200k級モデルで3〜4タスクが実績値)。Claudeはこの目安を依頼書で伝えるだけで、分割の中身は決めない
- バッチごとに「ompが完了報告 → Claude側レビュー → OK後にompがmainへマージ → 次バッチ」のゲートを回す。統合ブランチはバッチ単位(例: `feat/xxx-batchN`)で、コミット・マージ作業もompが行う
- 「コンテキストが厳しければタスク区切りで圧縮してよい。ただし依頼書の内容は保持すること」と明示する
- 裁量は明示的に与えると効く。「レース系は実測してから直す(計装先行)」「対応なし判断も可」のような指示に正しく応答する

## 完了報告の形式

依頼書に次の形式を指定しておくと、Claude側のポーリングが不要になる:

- 報告: `herdr-msg reply <replyヒントのアドレス> '<要約1行>。詳細=<結果ファイルパス>'`
- 結果ファイルの内容: タスクごとの変更概要・検証結果・報告にない副作用

## 監督側の作法

- ompの実行中、Claudeは working tree を変更しない(ファイル編集・git操作・フォーマッタ実行を含む。読み取りはOK)。ompはブランチ切替やマージも行うので、作業ツリーのHEADは途中で変わりうる
- レビューは作業ツリーの状態でなくコミット基準で行う(例: `git diff main..feat/xxx-batchN`)
- 報告の主張は鵜呑みにせず、check/testを自分で再実行して裏取りする。実行は `herdr agent get "$term"` でompがidleなのを確認してから
- テスト差分は `git diff | rg '^-.*assert'` などでアサーション削除を機械的に検出する(実装エージェントは期待値を緩めがち)
- ompからの設計・仕様の相談には方針レベルで助言し、決定はompに返す。プロダクト判断(公開インターフェース、互換性、スコープ等)はユーザーと相談してから答える
- 差し戻しは同じ宛先へ `herdr-msg` で修正依頼を送る。自分で直さない
- 返事が長時間来ないときは `herdr agent get "$term"` で `agent_status` を見る。`blocked` なら承認待ち、`idle` なのに報告が無ければ取りこぼしの可能性。`herdr pane read` で画面を確認してから対処し、再送はしない(pane-consult の禁止事項)
- バッチごとの経過とレビュー所見をユーザーに報告する

## 後始末

このスキルで新規に作ったペインだけ閉じる(既存の常駐ペインを流用した場合は閉じない)。全バッチ完了後、ユーザーが見終わったことを確認してから:

```bash
herdr pane close "$(herdr agent get "$term" | jq -r '.result.agent.pane_id')"
```
