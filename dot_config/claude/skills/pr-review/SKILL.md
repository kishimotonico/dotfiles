# pr-review

レビューのリーダーは自分(Opus)が務める。目標は、指摘を初回で出し切って五月雨式の差し戻しをなくすこと。レビュー本文の体裁、投稿方法、Backlogの扱いはプロジェクトのメモリやルールに従う。

## 流れ

1. 対象を確かめる。PR番号、ブランチ、head SHAを控える。メインのworktreeではcheckoutせず、`gh pr diff` か `git show <ref>:<path>`、必要なら専用worktreeで読む
2. 初回で出し切る。2〜3周回し、呼び出し元、影響範囲、テストの抜け、エラー処理、境界値、並行性まで洗う
    - 観点別の洗い出し、調査、動作確認はSonnetのサブエージェントに並列で任せる。指摘にするかどうかの判断は自分がやり、サブエージェントの報告はコードで裏を取る
    - 「実証済み」と書くのは、実際のコード経路で再現できた指摘だけ。直し方を提案するなら、それが同じ経路で成り立つかも確かめる
    - 粒度はPRの規模に合わせる。軽微なものは参考情報にとどめ、揚げ足取りはしない
    - ドキュメントの不備は差し戻し一択にしない。作成者に依頼する、こちらで巻き取る、suggestionで出す、別課題にする、から選ぶ
3. 指摘を反証する。指摘ごとにSonnetを別々に立て、主張と根拠の場所だけを渡して(結論は渡さない)、反証するつもりで検証させる。判定は「成立/一部成立/不成立」。取り下げるのは根拠の行を示せるときだけで、場当たり的に取り下げない
4. Fableに見直してもらう。変更の規模が大きいとき、設計に関わる指摘があるとき、Request Changesにするとき(特に再レビュー)は、Fableのサブエージェントに指摘と判定(差し戻し/コメントのみ/承認)の妥当性を見てもらう
5. Astraに最終確認してもらう。下書きが固まったら、下の手順で依頼する。Astraは念のための第三者で、修正のやり取りの途中には挟まない。ここで指摘が増えるようなら、2〜4が足りていなかったということ
6. 報告する。指摘を重大度順に並べ、そのまま貼れる下書きにしてscratchpadに置く。投稿はユーザーの確認を待つ

## 再レビュー

- 前回指摘の解消確認が中心だが、それだけで承認しない。新しく入った変更は初回と同じ観点で見る
- 再レビューで新しい指摘を出すのはレビュー側の落ち度になる。出すなら、初回で見落とした理由も説明する
- 枝葉末節は出さない。同じPRで一緒に直したほうがよい点は、ここでまとめて出す

## Astraへの依頼

herdrの別paneにいるCodex(Astra)へ、依頼ファイルとconsultで頼む。送受信の作法は pane-consult に従う。宛先はユーザーが指定したタブ名を使い、指定がなければ `codex` を渡す。

依頼ファイルはscratchpadに書く。Astraは会話の前提を持っていないので、このファイルだけで作業できるようにする。

- 対象: リポジトリのパス、PR番号、ブランチ、head SHA、読み方
- 役割: レビューだけをお願いする。編集、checkout、テストの実行、PRへの投稿、Backlogの更新はこちらが引き受ける。動作確認が必要なら手順をもらって、こちらのサブエージェントで試す
- 背景: PRの内容、経緯(再レビューなら前回の指摘と、`<前回SHA>..<今回SHA>` の差分範囲)、裏取り済みの事実
- 下書き: 自分のレビュー下書きのパス
- 見てほしいこと: 指摘の事実関係、直し方がそのまま成り立つか、判定の妥当性、見落とし。前回の自分の案に欠陥があったなら、同じ種類の誤りを特に疑ってもらう。追加の指摘は小出しにせず今回まとめて出してもらう
- 返し方: 指摘ごとに確度(確定/可能性)と根拠(ファイル:行)を付けて結果ファイルに書き、replyではパスと要約だけを返してもらう

consultは1行にまとめる。

```bash
herdr-msg consult <タブ名> 'PR #N のレビュー下書きの最終確認をお願いします。詳細は <依頼ファイル> にあります。レビューだけお願いし、投稿や編集はこちらで引き受けます。'
```

返事が来たら、Astraの指摘も鵜呑みにせずコードで裏を取ってから下書きに反映する。受領確認やお礼だけのreplyは送らない。
